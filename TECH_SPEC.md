### 1.5 JSON Column Conventions

SQLite does not have native array support. All list fields are stored as JSON text arrays. Application layer reads them via `json.loads()` and writes via `json.dumps()`. Domain tag filtering is done by loading the JSON array in Python and doing set intersection; this is acceptable because the dataset is bounded (hundreds of points, not millions).

## 2. Generator Engine Data Flow

### 2.1 Two-Level Generation Pipeline

```
[Experience File (Story Portfolio)]
       │
       ▼
[Parser] ──▶ Extracts YAML frontmatter → `knowledge_sources` table
       │     Extracts ## stories → list of Story objects
       │
       ▼
LEVEL 1: PER-STORY EXTRACTION
       │
       ├── For each Story:
       │   ├── Inject experience context (company, position, file context paragraph)
       │   ├── Inject story metadata hints (_Skills_, _Metrics_, _Team_)
       │   ├── LLM extracts STAR → CVPointCandidate(s) (1–3 points per story)
       │   └── Validator checks point-level rules
       │
       └── All candidates collected
              │
              ▼
       QnA REFINEMENT LOOP (per story)
              │
              ├── Ask targeted questions based on validation gaps
              ├── User answers → LLM regenerates → re-validate
              └── Repeat 2–3 rounds
              │
              ▼
LEVEL 2: EXPERIENCE-LEVEL REFINEMENT
       │
       ├── Merge duplicate candidates (embedding similarity > 0.85)
       ├── Split rich points (2+ distinct achievements in one candidate)
       ├── Drop weak points (vague scope, no clear contribution)
       ├── Re-order by estimated impact
       └── Flag coverage gaps (metadata skills not in any point)
              │
              ▼
[User Review] ──▶ Approve / Edit / Drop each refined point
       │
       ├── Approved ──▶ status = `approved` → Store in `cv_points`
       ├── Edited   ──▶ Inline edit → re-validate → store
       └── Dropped  ──▶ status = `archived`
```

### 2.2 Story Parsing Strategy

The parser reads an experience file as a **Story Portfolio**, not a dump.

**Structure parsed:**

```
ExperienceFile
├── YAML frontmatter (company, position, date, ...)
├── Context paragraph (optional free-form text before first ##)
└── Stories[]
    ├── Story 1
    │   ├── title: "## " heading text
    │   ├── narrative: all paragraphs until metadata or next ##
    │   ├── metadata: {skills, metrics, team} (optional, key-value pairs)
    │   └── source_file_id: from frontmatter
    ├── Story 2
    └── ...
```

**Parser behavior:**
- Splits on `## ` headings. Everything between two `##` headings is one `Story`.
- Metadata hints are lines starting with `_` and ending with `:` at the end of the story.
- The context paragraph (text before the first `##`) is injected into every story's prompt as background.
- The parser is idempotent: re-running it on the same file produces the same stories unless new `##` sections were added.

**Metadata hint extraction:**

```python
def extract_metadata(story_text: str) -> dict[str, str]:
    """Extract _Key_: value lines from the end of a story."""
    # Lines like:
    #   _Skills_: Python, Redis, Kubernetes
    #   _Metrics_: P95 latency 800ms → 120ms
    #   _Team_: 3 engineers, 6 weeks
```

### 2.3 Level 1: Per-Story Extraction

**Input:** One `Story` object (narrative + metadata + experience context)

**Prompt construction:**

```
You are a CV writing assistant. Read this story from a work experience
and extract distinct CV points.

Experience context:
{company} | {position} | {context_paragraph}

Story:
{story.narrative}

Metadata hints (may be incomplete):
Skills: {story.metadata.skills or "not provided"}
Metrics: {story.metadata.metrics or "not provided"}
Team: {story.metadata.team or "not provided"}

Instructions:
1. Extract up to 3 CV points from this story.
2. Each point = ONE specific achievement or responsibility.
3. If the story describes ongoing work without a clear one-time achievement,
   extract 1 responsibility-focused point.
4. Infer missing metadata from the narrative if possible.

Output: JSON array of CVPointCandidate
```

**Output:** `List[CVPointCandidate]` — 1 to 3 points per story. The LLM decides based on narrative richness.

### 2.4 Level 2: Experience-Level Refinement

**Input:** All `CVPointCandidate`s from one experience file.

**Operations:**

| Operation | Trigger | Action |
|-----------|---------|--------|
| Merge duplicates | Embedding similarity > 0.85 between two candidates | Keep the candidate with higher estimated impact; discard the other |
| Split rich points | One candidate contains 2+ distinct action verbs + 2+ distinct outcomes | Ask user: "Split into N points?" If yes, run N sub-prompts on the same story |
| Drop weak points | No clear action verb, vague scope, or no contribution stated | Flag for user: "This point feels thin — keep or drop?" |
| Re-order | After merge/split/drop | Sort by `impact_score` descending |
| Coverage check | Skills from metadata not found in any candidate bullet | Flag: "You listed {skill} but no point mentions it" |

**Why a separate refinement step?**
- Cross-story awareness: "Led team" appears in 3 stories → keep the best one
- Global balance: prevents 8 points from one rich story and 1 from a thin story
- User reviews a manageable set (~5–8 points per experience) instead of raw candidates

### 2.5 Error Handling & Retries

- **Instructor schema rejection:** If the LLM returns JSON that fails Pydantic validation, the error is logged, the raw response is stored in a debug artifact, and the story is re-submitted with an explicit correction prompt (max 2 retries).
- **Validation rule failures:** If `rendered_bullet` > 200 chars or contains pronouns, the validator constructs a specific correction prompt and loops back to the Draft Generator.
- **Missing metrics:** If `has_metrics` is false after validation, the point is flagged in QnA but **not blocked**. The user can skip the metric question.

## 3. Assembler & RenderCV Integration

### 3.1 Responsibilities

The assembler builds a RenderCV-compatible YAML file and invokes RenderCV's Python API to render it to PDF. This replaces the previous system boundary at `cv-output.yaml`.

### 3.2 RenderCV Pipeline

```
[Assembler builds Python dict]
       │
       ▼
[yaml.safe_dump] ──▶ cv-output.yaml (for inspection/debugging)
       │
       ▼
[build_rendercv_dictionary_and_model] ──▶ validated RenderCVModel
       │
       ▼
[generate_typst] ──▶ .typ file (intermediate)
       │
       ▼
[generate_pdf] ──▶ cv-output.pdf
```

### 3.3 RenderCV Entry Types Used

| Section | Entry Type | Required Fields | Optional Fields |
|---------|-----------|-----------------|-----------------|
| `experience` | ExperienceEntry | `company`, `position`, `highlights` | `date`, `start_date`, `end_date`, `location`, `summary` |
| `projects` | NormalEntry | `name`, `highlights` | `date`, `start_date`, `end_date`, `location`, `summary` |

**Role grouping (promotions):** When an experience file has multiple `roles` in its frontmatter and stories are tagged with `_Role_`, the assembler emits N `ExperienceEntry` objects for the same company — one per distinct role. RenderCV renders these as stacked entries. Points without a `_Role_` tag are assigned to the most recent role.
| `education` | EducationEntry | `institution`, `area`, `degree` | `date`, `start_date`, `end_date`, `location`, `highlights` |
| `publications` | PublicationEntry | `title`, `authors` | `doi`, `url`, `journal`, `date`, `summary` |
| `patents` | OneLineEntry | `number` | — |
| `invited_talks` | OneLineEntry | `reversed_number` | — |
| `honors` | OneLineEntry | `bullet` | — |
| `skills` | OneLineEntry | `label`, `details` | — |

### 3.4 Output Path Configuration

RenderCV output paths are controlled via `settings.render_command` in the YAML:

```yaml
settings:
  render_command:
    output_folder: rendercv_output
    pdf_path: OUTPUT_FOLDER/NAME_IN_SNAKE_CASE_CV.pdf
```

The assembler does not hard-code output paths. It respects whatever the user defines in `profile.yaml`'s `settings.render_command` block. If omitted, RenderCV uses defaults.

### 3.5 Error Handling

| Error | Source | Handling |
|-------|--------|----------|
| `RenderCVUserValidationError` | YAML schema mismatch | Catch, log validation errors with YAML locations, surface to user |
| `RenderCVUserError` | General rendering failure | Catch, log, surface to user |
| `jinja2.exceptions.TemplateSyntaxError` | Theme template bug | Catch, log template file + line number |
| `OSError` | Missing `typst` binary | Catch, suggest installing `rendercv[full]` |

### 3.6 Why Python API over CLI Subprocess

**Decision:** Use `rendercv.renderer` and `rendercv.schema.rendercv_model_builder` directly.

**Rationale:**
1. **No shell escaping issues** — file paths with spaces or special characters are handled natively.
2. **Structured exceptions** — `RenderCVUserValidationError` contains line/column metadata we can surface to the user.
3. **No temp file race conditions** — the pipeline operates on in-memory strings and Path objects.
4. **Still inspectable** — we call named functions with known signatures; nothing is hidden.

**Alternative considered:** Shell out to `rendercv render cv-output.yaml`. Rejected because subprocess error handling is coarse-grained and the user can't see which YAML line caused a validation failure.

## 4. Custom Vector Search (No Vector DB)

### 4.1 Embedding Model & Dimensionality

**Model:** Ollama-hosted `nomic-embed-text` (768 dimensions) or `mxbai-embed-large` (1024 dimensions). Configurable via `.env` (`EMBEDDING_MODEL`).

**Generation:** The `llm_client` module exposes an `embed(text: str) -> list[float]` method that calls the Ollama `/api/embeddings` endpoint and returns a Python list of floats.

### 4.2 Storage Format

Embeddings are stored in the `cv_points.embedding` column as a SQLite `BLOB`.

- **Normalization:** Embeddings are L2-normalized at write-time before storage. This makes cosine similarity equivalent to a dot product at query time, keeping the math explicit and the code simpler.
- **Serialization:** Convert the normalized float list to a NumPy `float32` array, then call `array.tobytes()`.
- **Deserialization:** Read the BLOB, reconstruct via `np.frombuffer(blob, dtype=np.float32)`.
- **Rationale:** `BLOB` is compact and fast. A 768-dim float32 vector = 3072 bytes. 1000 points = ~3 MB, trivial for in-memory loading.

### 4.3 Cosine Similarity Search

At query time, all embeddings for `approved` points are loaded into memory as a single NumPy matrix.

**Formula:**

Because embeddings are L2-normalized at write-time, cosine similarity reduces to a dot product:

```python
import numpy as np

def cosine_similarity(query_vec: np.ndarray, matrix: np.ndarray) -> np.ndarray:
    """Compute cosine similarity between query and all rows in matrix.

    Precondition: both query_vec and every row in matrix are L2-normalized.
    """
    return np.dot(matrix, query_vec)
```

**Normalization at query time:** The query embedding is normalized before search: `query_vec = query_vec / np.linalg.norm(query_vec)`.

**Top-k Retrieval:**
1. Embed the query (domain tag string or JD text).
2. Load `embedding` blobs for all `approved` points into a NumPy matrix.
3. Compute cosine similarities.
4. Return the top-k point IDs with their scores.

**Complexity:** O(n * d) where n = number of approved points, d = embedding dimension. With n < 10,000 and d = 768, this runs in milliseconds on a modern CPU. No approximate indexing is needed.

### 4.4 Redundancy Detection

Redundancy uses the same embedding + cosine similarity approach:

1. After a new point is approved, generate its embedding.
2. Compute cosine similarity against all existing `approved` points.
3. If similarity > `REDUNDANCY_THRESHOLD` (default 0.85), insert a row into `redundancy_pairs` with `resolution = 'pending'`.
4. The CLI surfaces pending pairs for user review.

### 4.5 Embedding Text Composition

The `embedding` on a `CVPoint` is computed from a **concatenated string**, not from a single field. This decision affects both retrieval quality and redundancy detection accuracy.

**Composition rule (concatenated in this order, separated by `" | "`):**

```
{rendered_bullet} | Context: {components.context} | Result: {components.result} | Skills: {skills_utilized}
```

**Rationale for each component:**

| Component | Why include it? |
|---|---|
| `rendered_bullet` | Captures the polished, action-oriented phrasing. The final form a recruiter reads. |
| `components.context` | Adds domain, scope, and technology stack. Critical for matching JD requirements like "fintech backend" or "Kubernetes experience." |
| `components.result` | Adds impact signal. JDs often search for proven outcomes ("reduced latency," "increased revenue"). |
| `metadata.skills_utilized` | Surfaces technologies that may not appear in the bullet. E.g., bullet says "built API" but skills say "FastAPI, Pydantic, SQLAlchemy." |

**Why `extended_context.situation` and `task` are excluded:**

`Situation` and `task` are STAR framing for the *generator* LLM, not searchable keywords. A JD query never asks for "the company had scaling problems" — it asks for "built scalable systems." Including them adds noise and can create false similarity between points with similar situations but different outcomes.

**Why `domain_tags` are excluded:**

Domain tags are controlled-vocabulary labels (e.g., `fintech`, `backend_engineering`). They carry less semantic signal than the free-text `context` and `result`, and the embedding model already captures domain concepts from those fields. Including them would be redundant.

**Length budget:**

Even with all four components, the concatenated text is typically under 400 characters — well within the context window of sentence embedding models (`nomic-embed-text` handles up to 2048 tokens). No truncation is required.

## 5. Evaluation Metrics & Benchmarks

### 4.1 Generator Extraction Evaluation

**Purpose:** Compare prompt variants, model variants, or temperature settings for the Draft Generator.

**Metrics:**
- **Schema Adherence Rate:** Percentage of outputs that pass Pydantic validation on the first try (no retries). Target: > 90%.
- **Validation Pass Rate:** Percentage of outputs that pass all validator rules (verb-first, length, pronouns, metrics) on the first try. Target: > 85%.
- **Human Impact Score Correlation:** Pearson correlation between LLM-as-judge `impact_score` and a human-rated impact score on a labeled test set. Target: > 0.75.
- **ATS Keyword Coverage:** Fraction of industry keywords present in the `rendered_bullet` compared to a reference keyword list for the domain. Target: > 0.80.

**Benchmark Harness (`benchmarks/generator_extraction_eval.py`):**
- Input: A JSONL file containing raw dump chunks and a human-approved "gold" CV point for each.
- Procedure: Run each configuration (prompt A vs prompt B, model X vs model Y) across the test set. Store raw outputs, scores, and pass/fail flags.
- Output: A JSONL file with one record per (test_case, config) pair, plus an aggregate summary report.

### 4.2 Judge Quality Evaluation

**Purpose:** Validate that the LLM-as-judge produces stable, meaningful scores.

**Metrics:**
- **Inter-Rater Reliability:** Cohen's kappa between LLM-as-judge scores (binned into low/medium/high) and human baseline scores. Target: > 0.65.
- **Score Variance (Stability):** Standard deviation of `impact_score` across 5 independent evaluations of the same point with the same prompt. Target: < 0.5.
- **Rank Preservation:** Spearman correlation between judge rankings and human rankings on a shuffled pair-comparison test. Target: > 0.80.

**Benchmark Harness (`benchmarks/judge_quality_eval.py`):**
- Input: A labeled set of 50 CV points with human scores.
- Procedure: Run the judge N times per point. Compute stability and correlation metrics.
- Output: Variance report and correlation matrix.

### 4.3 RAG Retrieval Evaluation

**Purpose:** Measure how well the custom numpy cosine similarity retrieval finds relevant points.

**Metrics:**
- **Precision@k:** Of the top-k retrieved points, what fraction are labeled relevant? Target: > 0.70 for k=5.
- **Recall@k:** Of all labeled relevant points, what fraction appear in the top-k? Target: > 0.60 for k=5.
- **Mean Reciprocal Rank (MRR):** Average of `1 / rank_of_first_relevant` across queries. Target: > 0.65.

**Benchmark Harness (inline in `benchmarks/` or separate script):**
- Input: A set of domain/JD queries and a labeled ground-truth mapping of relevant point IDs per query.
- Procedure: Embed queries, run retrieval, compare returned IDs against ground truth.
- Output: Per-query metrics and aggregate averages.

### 4.4 Result Storage

All benchmark outputs are written to `benchmarks/results/` as timestamped JSONL files. Each record includes:
- `timestamp`
- `benchmark_name`
- `config` (model, prompt version, temperature, etc.)
- `metrics` (the computed values)
- `raw_outputs` (optional, for debugging)

The `benchmarks/results/` directory is gitignored to avoid polluting the repo with large artifacts.
